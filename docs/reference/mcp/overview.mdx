| Endpoint | `https://mcp.langmail.me/mcp` |
| Transport | Streamable HTTP |
| Authorization | OAuth 2.1 bearer token — see [How authorization works](/connect/authorization) |
| Server name | `langmail-mcp` |
| Surface | 42 tools; one MCP resource (the email viewer for [`preview_email`](/reference/mcp/preview-email)); no prompts |

The server is stateless: every request is authenticated independently, and all tools operate on the mailbox of the user who granted the token.

## Tools

### Email — read

| Tool | Purpose |
|---|---|
| [`search_emails`](/reference/mcp/search-emails) | Structured search — free text plus email-type, sender, date-range, read-state, starred, and mailbox filters |
| [`get_email`](/reference/mcp/get-email) | Fetch one message's recipients, folders and full plain-text body |
| [`preview_email`](/reference/mcp/preview-email) | Show one message to the user as a rendered document, such as a ticket or an invoice, without its body entering the agent's context |
| [`get_thread`](/reference/mcp/get-thread) | List every message in a conversation, oldest-first |
| [`download_attachment`](/reference/mcp/download-attachment) | Mint a short-lived download URL for one attachment — bytes stay out of the conversation |
| [`download_email`](/reference/mcp/download-email) | Mint a short-lived download URL for one message's raw source (`.eml`) — bytes stay out of the conversation |
| [`upload_attachments`](/reference/mcp/upload-attachments) | Mint short-lived upload URLs for local files to attach to a draft — bytes stay out of the conversation |

Message content comes from whoever sent it. Agents are told, in the tool descriptions themselves, to treat it as data to read and report on rather than as instructions to follow.

### Email — file

| Tool | Purpose |
|---|---|
| [`archive_emails`](/reference/mcp/archive-emails) | Take messages out of the Inbox, Junk and Trash and into Archive (a Junk message only when the user says it is not spam); Sent, other folders, read state and flags untouched |
| [`move_emails`](/reference/mcp/move-emails) | Move messages into a named folder, replacing whatever folders they were in. Refuses Trash |
| [`trash_emails`](/reference/mcp/trash-emails) | Move messages to the Trash. Recoverable until Trash is emptied |
| [`unsubscribe_from_list`](/reference/mcp/unsubscribe-from-list) | Unsubscribe the user from the list one message came from: sends the RFC 8058 one-click request, never mail. Refuses Junk |

Filing is split by verb, not by destination, because the annotations describe a tool unconditionally: one move tool that could reach Trash would carry `destructiveHint` onto every archive. `archive_emails`, `move_emails` and `trash_emails` each take a batch of up to 50 message ids and report the outcome per id, so a stale id in a list is named rather than failing the batch; folders are never created — an unknown name comes back with the folders that exist — and flags (read state, to-dos, stars) are never touched. `unsubscribe_from_list` takes a single id instead, because the consent it needs is per sender rather than per message.

### Email — flags

| Tool | Purpose |
|---|---|
| [`mark_emails`](/reference/mcp/mark-emails) | Set or clear the read, to-do and starred flags — folders and types untouched |

Flags are their own verb: reading a message with `get_email`, `get_thread` or `search_emails` leaves its read state as it was, filing leaves every flag as it was, and `mark_emails` sets read, to-do and starred when the agent decides to.

### Email — compose and send

| Tool | Purpose |
|---|---|
| [`create_draft`](/reference/mcp/create-draft) | Compose a message — or a correctly threaded reply — and stage it in Drafts without sending |
| [`get_draft`](/reference/mcp/get-draft) | Read a staged draft back, blind-copied recipients included |
| [`list_drafts`](/reference/mcp/list-drafts) | List what is staged in Drafts, newest first, with the draft id the other draft tools take |
| [`update_draft`](/reference/mcp/update-draft) | Edit a staged draft, keeping its draft id; on a reply, the quoted original stays below the new text |
| [`send_draft`](/reference/mcp/send-draft) | Send a staged draft. Irreversible |
| [`delete_draft`](/reference/mcp/delete-draft) | Permanently delete an unsent draft |
| [`reply_to_message`](/reference/mcp/reply-to-message) | Reply and send in one call, threading derived from the original. Irreversible |
| [`forward_message`](/reference/mcp/forward-message) | Forward and send in one call, with the original's attachments, formatting and headers. Irreversible |

**Stage by default, send explicitly.** Composition and delivery are separate tools, so an agent that has written a message has not thereby sent one — the default outcome of asking an agent to write mail is a draft in the user's Drafts folder, indistinguishable from one they typed. That is a posture Langmail can afford precisely because it is the mail client: the confirmation step happens in-product rather than being deferred to somebody else's UI.

Threading is never assembled by the agent. Pass the id of the message being answered and the recipients, the `Re:` subject, and the `In-Reply-To`/`References` headers are derived server-side from that message.

Duplicate delivery is guarded three ways, because each closes a window the others leave open: a sent message no longer looks like a draft (server-side, no client cooperation needed); an in-flight send reserves its draft, so a retry that arrives *before* the first call answers is refused; and an `idempotencyKey` replays the first answer for a retry that arrives after. Keys are scoped per tool — reusing one across `create_draft` and `send_draft` is not a retry. A send that fails without saying whether the mail went out is reported as unknown and refused rather than retried. See [`send_draft`](/reference/mcp/send-draft) for the full picture.

Drafts carry attachments, named either by the `blobId` of a file already in the mailbox or as base64 `content` for one the agent generated. The `blobId` form is the one to reach for: it re-references a blob the server already holds, so forwarding an attachment transfers nothing and the bytes never pass through the model's context. There is no path parameter — the MCP server is a remote service and cannot read the agent's filesystem.

There is no bulk or campaign sending, and no direct `send_message` — `create_draft` followed by `send_draft` expresses the same intent with an inspection point in the middle. Listing drafts has its own tool, [`list_drafts`](/reference/mcp/list-drafts), because `search_emails` returns message ids, and an edited draft's message id changes on every edit while its draft id does not.

Drafts cannot yet be scheduled for later delivery, and there is no send-and-undo window.

### Mail rules — read-write

| Tool | Purpose |
|---|---|
| [`preview_mail_rule`](/reference/mcp/preview-mail-rule) | Validate a proposed rule and estimate matching existing mail — changes nothing |
| [`create_mail_rule`](/reference/mcp/create-mail-rule) | Create a persistent rule from natural language, optionally backfilling existing mail |
| [`list_mail_rules`](/reference/mcp/list-mail-rules) | List every rule with its id, name, enabled state, conditions, and actions |
| [`update_mail_rule`](/reference/mcp/update-mail-rule) | Rename, enable/disable, or replace a rule's conditions/actions in place |
| [`delete_mail_rule`](/reference/mcp/delete-mail-rule) | Delete a rule by id |

Rules live as one managed Sieve script in the user's own account and run server-side on every delivery. Future automation and historical application are distinct: rules affect future mail by default, and backfills over existing mail are explicit, scoped (Inbox or all mail), and confirmation-gated when large.

### Contacts — read-write

| Tool | Purpose |
|---|---|
| [`search_contacts`](/reference/mcp/search-contacts) | Resolve a name, partial name, address, or organization to known contacts, ranked by interaction recency and frequency |
| [`list_upcoming_birthdays`](/reference/mcp/list-upcoming-birthdays) | List whose birthday falls in the next N days, across every address book |
| [`create_contact`](/reference/mcp/create-contact) | Create a contact from a name plus optional addresses, phone numbers, postal addresses, organization, birthday, and note |
| [`update_contact`](/reference/mcp/update-contact) | Change named fields of a stored contact, leaving everything else untouched |
| [`merge_contacts`](/reference/mcp/merge-contacts) | Fold duplicate contacts of one person or organization into the one to keep, with their addresses, notes and history |
| [`delete_contact`](/reference/mcp/delete-contact) | Delete a contact by id |

Most contacts are collected automatically from mail headers and calendar attendees, alongside any address books on the account — so someone who has already written to you is findable without any setup. The write tools cover the people that derivation structurally cannot reach: someone you met in person, spoke to on the phone, or know through a channel Langmail does not see. Every record carries a `source` marker (`derived`, `authored`, `imported`) because a confidence rating means different things across them, and collection only ever fills blanks on a record — it never overwrites a field a user typed.

Writes to contacts are durable: the address book syncs to every device connected over CardDAV, so a contact an agent creates appears on the user's phone. The tool annotations reflect this — `create_contact` and `update_contact` are account writes, `merge_contacts` and `delete_contact` are destructive — so a client can gate on the annotations without hard-coding tool names.

### Calendar — read-write

| Tool | Purpose |
|---|---|
| [`list_calendars`](/reference/mcp/list-calendars) | List calendars with their CalDAV URLs, colors and who each is shared with |
| [`create_calendar`](/reference/mcp/create-calendar) | Create a new calendar |
| [`update_calendar`](/reference/mcp/update-calendar) | Rename or recolor a calendar |
| [`share_calendar`](/reference/mcp/share-calendar) | Share a calendar with a person at busy times only or full details, through a secret link |
| [`stop_sharing_calendar`](/reference/mcp/stop-sharing-calendar) | Stop a person's share, emptying their link |
| [`list_calendar_events`](/reference/mcp/list-calendar-events) | List events, optionally within a time window |
| [`create_calendar_event`](/reference/mcp/create-calendar-event) | Create an event or recurring series, with invitations to any attendees |
| [`update_calendar_event`](/reference/mcp/update-calendar-event) | Reschedule or edit an event by passing only the fields that change, and notify attendees (or not) |
| [`delete_calendar_event`](/reference/mcp/delete-calendar-event) | Delete an event and send cancellations |
| [`move_calendar_events`](/reference/mcp/move-calendar-events) | Move events to another calendar, unchanged and without notifying anyone |
| [`respond_to_event`](/reference/mcp/respond-to-event) | RSVP to an invitation — accept, decline, or tentative |

## Risk annotations

Every tool carries MCP [tool annotations](https://modelcontextprotocol.io/), so a client can decide which calls need a confirmation step without hard-coding tool names — the only version of that check that survives new tools being added. Two hints carry the decision:

- `openWorldHint` — the call reaches someone outside the user's own account: a recipient, an attendee, an iMIP notice.
- `destructiveHint` — the call cannot be taken back: it removes something, or it hands something to a third party.

| Class | Hints | Tools |
|---|---|---|
| Read-only | `readOnlyHint: true` | every `search_*`, `get_*`, `list_*`, plus `preview_email`, `download_attachment`, `download_email` and `preview_mail_rule` |
| Account write | both hints `false` | `create_draft`, `upload_attachments`, `archive_emails`, `move_emails`, `mark_emails`, `create_contact`, `update_contact`, `create_calendar`, `update_calendar`, `move_calendar_events` |
| Account destructive | `destructiveHint: true` | `update_draft`, `delete_draft`, `trash_emails`, `delete_mail_rule`, `merge_contacts`, `delete_contact`, `stop_sharing_calendar` |
| Outward write | `openWorldHint: true` | `create_mail_rule`, `update_mail_rule`, `create_calendar_event`, `respond_to_event` |
| Outward destructive | both hints `true` | `send_draft`, `reply_to_message`, `forward_message`, `update_calendar_event`, `delete_calendar_event`, `unsubscribe_from_list`, `share_calendar` |

Staging is deliberately distinguishable from sending on the hints alone: `create_draft` is an account write, `send_draft` is outward destructive. `update_draft` counts as destructive because editing a draft replaces the message — the previous version does not come back, and the draft being edited need not be one the agent wrote.

The mail-rule writers count as outward, not account-local, because a rule may carry a `forward` action — which redirects a copy of every matching future message to an arbitrary address. A static annotation has to describe what a tool *can* do, and installing a persistent forwarding rule is the furthest outward reach on this surface. `share_calendar` counts as outward because it hands a live view of a calendar to whoever holds the link, and as destructive because, given an address, it emails that link at once, which cannot be taken back.

The table describes the tools at Everything. At Change, never send, the event and mail-rule writers are account-only and carry `openWorldHint: false` ([Access levels](#access-levels)).

`idempotentHint` is `false` on every write. The composition tools accept an `idempotencyKey` that does make a retry safe, but the hint describes the tool unconditionally, and a caller that omits the key gets a second send.

## Access levels

The server offers an agent the tools of one access level. Each level adds tools to the one below it. A [self-hosted server](https://github.com/langmail/langmail-mcp/blob/main/docs/self-hosted.md#access-levels) takes the same levels from its `--access` setting:

| Level | `--access` | What the agent can do | Tools added |
|---|---|---|---|
| Read only | `read-only` | Read the account: search, read, preview, download, list | `search_emails`, `get_email`, `get_thread`, `preview_email`, `download_attachment`, `download_email`, `list_drafts`, `get_draft`, `list_mail_rules`, `preview_mail_rule`, `search_contacts`, `list_upcoming_birthdays`, `list_calendars`, `list_calendar_events` |
| Change, never send | `no-send` | Also change the account itself, without reaching anyone else: file and flag mail, stage drafts, upload attachments, manage calendars, personal events, contacts and mail rules, end a calendar share | `archive_emails`, `move_emails`, `trash_emails`, `mark_emails`, `upload_attachments`, `create_draft`, `update_draft`, `delete_draft`, `create_mail_rule`, `update_mail_rule`, `delete_mail_rule`, `create_calendar`, `update_calendar`, `stop_sharing_calendar`, `create_calendar_event`, `update_calendar_event`, `delete_calendar_event`, `move_calendar_events`, `create_contact`, `update_contact`, `merge_contacts`, `delete_contact` |
| Everything | `everything` | Also reach other people: send mail, unsubscribe, share a calendar, invite and answer invitations, forward mail by rule | `send_draft`, `reply_to_message`, `forward_message`, `unsubscribe_from_list`, `share_calendar`, `respond_to_event` |

At Change, never send, five tools have a narrowed form that handles only what stays in the account. The update and delete tools refuse a stored event or rule that already reaches other people:

- [`create_calendar_event`](/reference/mcp/create-calendar-event#at-change-never-send), [`update_calendar_event`](/reference/mcp/update-calendar-event#at-change-never-send) and [`delete_calendar_event`](/reference/mcp/delete-calendar-event#at-change-never-send) handle personal events, ones nobody else is on, and notify nobody.
- [`create_mail_rule`](/reference/mcp/create-mail-rule#at-change-never-send) and [`update_mail_rule`](/reference/mcp/update-mail-rule#at-change-never-send) offer every action except `forward`.

The level limits only what the agent does through this server. The credential the server acts with keeps full rights on the mail server: the OAuth bearer token on `mcp.langmail.me`, the app password on a self-hosted server. On `mcp.langmail.me` a level changed in Langmail holds for the agent's next request a minute later at most, without connecting it again. Until Langmail lets the user choose it, every agent connects at Everything.

## Result conventions

- Every tool returns a single plain-text content block, formatted for direct agent consumption — compact and stable, no JSON envelope to parse. The one addition is `preview_email`, which also returns `structuredContent` with the message's metadata and carries the rendered body in `_meta` for the client.
- List results are numbered and include the identifiers (`id`, `uid`, `calendarUrl`) that downstream tools take.
- Search and thread results include snippets but omit full message bodies by design; full bodies come from `get_email` only.
- Failures return a text block with the MCP `isError` flag and a one-line reason, for example `Email not found: M123` or `Calendar not found: <url>`. Where a failure could be mistaken for a partial send, the reason says so explicitly — `Nothing was sent.`
- Attachment bytes never appear in a tool result. `download_attachment` returns metadata plus a short-lived capability URL under `https://mcp.langmail.me/attachments/…`; the file is fetched out-of-band from that URL (e.g. with `curl -o`) straight to disk; `download_email` does the same for a whole message's raw source. `upload_attachments` is the other direction: the agent PUTs a local file to a URL under `https://mcp.langmail.me/attachments/uploads/…` and gets back a `blobId` for `create_draft`.

## Datetimes

- Email filters (`after`, `before`) take **UTC** ISO 8601 timestamps ending in `Z`.
- Calendar times (`start`, `end`, `until`) take ISO 8601 **with an offset**, so events keep their intended local time — `2026-07-14T10:00:00+02:00` or `2026-07-14T08:00:00Z`.
